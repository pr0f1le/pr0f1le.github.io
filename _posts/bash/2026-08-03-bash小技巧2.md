## `Here Doc`, `Here String`

`Here Doc` 是我们常用的一种将多行文本作为输入字符串的重定向方式

```bash
cat > tmp <<EOF
hello
this is a tmp file
end
EOF

# 检查一下
cat tmp

# 输出
hello
this is a tmp file
end
```

但是其实 `Here Doc` 也是会进行参数展开的

```bash
name=world

cat > tmp <<EOF
$(date +%F)
hello $name
EOF

# 检查一下
cat tmp

# 输出
2026-08-03
hello world
```

如果不希望进行参数展开，我们很容易想到应该使用双引号，但不是在 `Here Doc` 内部，
而是应该在 `EOF` (或者你喜欢的)标识符前后添加单引号或双引号。

```bash
name=world

cat > tmp <<"EOF"
$(date +%F)
hello $name
EOF

# 检查一下
cat tmp

# 输出
$(date +%F)
hello $name
```

这在某些时候可以避免一些麻烦，例如希望写一点简短的 bash 脚本的时候。

`Here String` 是更清爽一点的 `Here Doc`，因为它不需要结束标识符，在脚本中很好用

```bash
name=world
str="hello $name
this is a multi-line str
bye
"

grep 'str' <<< $str

# 输出
this is a multi-line str
```

在这里跟 `echo "$str" | grep 'str'` 效果一样，但是省去一次 `echo` 命令的加载运行等

而如果要使用 `Here Doc`，则需要

```bash
name=world
str="hello $name
this is a multi-line str
bye
"

grep 'str' <<EOF
$str
EOF

# 输出
this is a multi-line str
```

可以看出 `Here String` 更加简洁。

此外需要说明的是，`Here Doc` 是符合 POSIX 标准的，这意味着它可以在任意 shell 中
使用，而 `Here String` 是 POSIX 标准外的，使用时要注意使用的是什么 shell。

## `>()` 和 `<()` 进程替换

进程替换也就是命令替换，一样一样的，就是我们平常使用的 `today=$(date +%F)` 等等。

但是有些命令敲起来会觉得很繁琐，例如我们想同时查找一份输出中的两个模式

```bash
cat > /tmp/tmp.log <<EOF
WARN: smth goes wrong but i can handle it
ERROR: help me
WARN: it's ok
ERROR: i can't do this
WARN: invalid input
ERROR: no!!!!!!!!!!!
EOF

log_content=$(cat /tmp/tmp.log)

grep WARN <<< $log_content
grep ERROR <<< $log_content

# 输出
WARN: smth goes wrong but i can handle it
WARN: it's ok
WARN: invalid input
ERROR: help me
ERROR: i can't do this
ERROR: no!!!!!!!!!!!
```

可以看到这里我们必须将 `cat` 的结果存储在一个变量中，如果要使用管道就需要调用
两次 `cat` 命令。虽然这不是什么大问题，但是我们需要做出一点点妥协。

一种更优雅的进程替换方式是使用 `>()` 和 `<()`。

一看就知道这跟我们的 `>` 和 `<` 输入输出重定向有关。

重写上面的例子

```bash
cat > /tmp/tmp.log <<EOF
WARN: smth goes wrong but i can handle it
ERROR: help me
WARN: it's ok
ERROR: i can't do this
WARN: invalid input
ERROR: no!!!!!!!!!!!
EOF

tee >(grep WARN > /tmp/warn.log) >(grep ERROR > /tmp/error.log) < /tmp/tmp.log > /dev/null

cat /tmp/warn.log /tmp/error.log
# 输出
WARN: smth goes wrong but i can handle it
WARN: it's ok
WARN: invalid input
ERROR: help me
ERROR: i can't do this
ERROR: no!!!!!!!!!!!
```

需要注意的是，`tee` 命令接受的参数是文件，输入是 `stdin`，输出是参数中
的文件和 `stdout`。在上面的例子中，我们使用重定向将文件输入到 `tee` 并忽略了
它的标准输出。

那么可以明确的一点是，`>()` 进程替换的结果不是重定向，而是文件。

用一个例子来清晰地理解

```bash
ls >(cat)

# 输出
/dev/fd/63 # 文件描述符的数字可能不一样
```

可以看到实际上替换的结果是一个文件描述符。

详细解释一下这个很短但是很费解的命令：

1. `ls >(...)` 将进程替换为空闲的文件描述符，这里是 `/dev/fd/63`
替换结果为 `ls /dev/fd/63`
2. `cat` 从自己的 `stdin` 也是 `ls` 的 `/dev/fd/63` 读取内容，直接
读取到文件尾
3. `cat` 没有输出，`ls` 输出 `/dev/fd/63`

实际上进程替换内外输出到终端的顺序不一定，甚至可能交叉，最好不要所有输出都往终端送

通过 `strace` 可以看到

```bash
# 追踪 ls
in> strace --trace=write,execve ls >(cat)

execve("/usr/bin/ls", ["ls", "/dev/fd/63"], 0x7fff3fc0c990 /* 62 vars */) = 0
write(1, "/dev/fd/63\n", 11)            = 11

# 追踪 cat
in> ls >(strace --trace=execve,read cat)

read(3, "\177ELF\2\1\1\3\0\0\0\0\0\0\0\0\3\0>\0\1\0\0\0\300\255\2\0\0\0\0\0"..., 832) = 832
read(0, "", 131072)                     = 0

# 同时追踪，输出混在一起
in> strace --trace=execve,write ls >(strace --trace=execve,read cat)

execve("/usr/bin/cat", ["cat"], 0x7ffcbeffdb78 /* 62 vars */execve("/usr/bin/ls", ["ls", "/dev/fd/63"], 0x7ffe551ccf40 /* 62 vars */) = 0
) = 0
read(3, "\177ELF\2\1\1\3\0\0\0\0\0\0\0\0\3\0>\0\1\0\0\0\300\255\2\0\0\0\0\0"..., 832) = 832
read(0write(1, "/dev/fd/63\n", 11/dev/fd/63
)            = 11
+++ exited with 0 +++
, "", 131072)                     = 0
```

讲完了 `>()` 再讲一讲 `<()`，可以很明确的是，`<()` 的替换结果一定也是文件

```bash
ls <(:) >(:)

# 输出
/dev/fd/62
/dev/fd/63
```

这个例子其实比前面那个容易理解，因为我们只使用了一个什么都不做的函数 `:` 占位，
清清楚楚地看到了替换结果。

它的用途自然就是将命令的输出作为输入写入匿名文件(文件描述符)，并作为参数传递给命令

例如

```bash
mkdir -p /tmp/test1
mkdir -p /tmp/test2
touch /tmp/test1/{1..3}
touch /tmp/test2/{1..4}
diff <(ls /tmp/test1) <(ls /tmp/test2)

# 输出
3a4
> 4
```

`diff` 这种接受两个文件作为参数的命令很难使用管道来完成一些流水线操作，但是
使用 `<()` 就很合适。

要注意的是，`<()` 和 `>()` 也不是 POSIX 标准，在 POSIX 标准下需要使用命名管道等
来完成相同操作。

## 使用文件描述符打开文件

bash 可以使用 `exec` 将一个文件描述符绑定到文件上，实现打开文件的效果

直接上例子

```bash
cat > /tmp/tmp.log <<EOF
WARN: smth goes wrong but i can handle it
ERROR: help me
WARN: it's ok
ERROR: i can't do this
WARN: invalid input
ERROR: no!!!!!!!!!!!
EOF

exec 3< /tmp/tmp.log

while read -u 3 line; do
    echo $line
done

# 输出
WARN: smth goes wrong but i can handle it
ERROR: help me
WARN: it's ok
ERROR: i can't do this
WARN: invalid input
ERROR: no!!!!!!!!!!!
```

这里我们使用的是读模式打开的文件，用写模式就是 `3>`，读写模式就是 `3<>`。
这里 3 和 `>` 等重定向符号要紧贴，否则会被识别为命令。

用文件描述符打开有一个好处是，bash 会维护这个文件描述符的状态，例如

```bash
cat > /tmp/tmp.log <<EOF
WARN: smth goes wrong but i can handle it
ERROR: help me
WARN: it's ok
ERROR: i can't do this
WARN: invalid input
ERROR: no!!!!!!!!!!!
EOF

exec 3< /tmp/tmp.log

echo "first line"
read -u 3 line
echo "$line"

echo "second line"
read -u 3 line
echo "$line"

# 输出
first line
WARN: smth goes wrong but i can handle it
second line
ERROR: help me
```

脚本中可以一行一行慢慢处理这个文件，就像在 C 等语言中读取文件的每一行一样。

要写入文件描述符需要用 `>&3` 表示写入的不是文件 3 ，而是文件描述符 3 。

```bash
exec 3> /tmp/tmp1
echo "hello" >&3

cat /tmp/tmp1 > /tmp/tmp2

exec 3< /tmp/tmp2
read -u 3 line
echo "$line"

# 输出
hello
```

另外，这个例子里使用了两次文件描述符 3 ，bash 自动将这个文件描述符
从写入 `/tmp/tmp1`{:.filepath} 变为读取 `/tmp/tmp2`{:.filepath} ，
并且关闭了旧的文件。

这是默认行为，不会报错，但是有时为了语义明确，避免写入或读取错误的文件，可以
使用 `exec 3>&-` 手动关闭文件描述符。

```bash
exec 3< /tmp/tmp2
read -u 3 line
echo "$line"

exec 3>&-

read -u 3 line

# 输出
hello
/tmp/test.sh: 第 14 行：read: 3: 无效的文件描述符: 错误的文件描述符
```

这样会直接报错，及时关闭文件描述符可以避免在一些稍长的脚本中造成错误。

一般来说，0 是标准输入，1 是标准输出，2 是标准错误，3-9 是空闲的文件描述符，基本上
可以随意使用。

### 扩展用法

`exec 3<> /path/to/file` 的形式是符合 POSIX 标准的，bash 等还实现了更通用友好的
使用方式。

```bash
echo hello > /tmp/tmp1

exec {fd}< /tmp/tmp1
echo $fd
read -u $fd line
echo "$line"

exec {fd}>&-

[ -e "/proc/$$/fd/$fd" ] || echo "fd closed"

# 输出
10
hello
fd closed
```

使用 `exec {fd}<> /path/to/file` 可以自动分配空闲文件描述符并赋值给 `fd` ，后续
读取和写入可以直接用 `$fd` 替换文件描述符的位置，但是关闭需要用 `{fd}>&-` 的形式。

这种方式是不符合 POSIX 的用法，需要注意。

## COPROC

`coproc` 是我在浏览 bash 的 man pages 时无意间发现的。从名字看，这是一个协程，
而事实上也确实是。

bash 的 `coproc` 也不是 POSIX 标准，而且各个 shell 的实现各不相同，再加上平常
我们很难遇到需要用到协程才能解决问题的脚本，因此它的出场率并不高。

但这也是一个 bash 内实现了的有趣的特性，我们不妨挖掘一下。

`coproc` 会运行一个命令并将其挂在后台，同时自动处理输入输出重定向。也就是说
程序本身的行为与使用 `&` 将其挂在后台时相同，只是将输入输出自动重定向到了特
定的位置。

man page 中命令的写法为

> coproc [NAME] command [redirections]

如果不指定 `NAME` ，默认为 `COPROC`

推荐写法为

> coproc NAME { command [redirections]; }

其中写到

> If command is a compound command, NAME is optional. The word following  
> coproc determines whether that word is interpreted as a variable name:  
> it is interpreted as NAME if it is not a reserved word that introduces  
> a compound command.  If command is a simple command, NAME is not  
> allowed; this is to avoid confusion between NAME and the first word of  
> the simple command.

意思是说，如果命令是简单命令，那么 `NAME` 强制失效，如果是复合命令，`NAME` 才
可选，这可以避免分辨简单命令的第一个单词是 `NAME` 还是要调用的命令。

```bash
in> coproc L ls

bash: 行 1: L: 未找到命令
```

但是这样会导致所有简单命令的标识符 `NAME` 都为 `COPROC`。

这会有什么问题呢？

> The standard output of command is connected via a pipe to a file  
> descriptor in the executing shell, and that file descriptor is assigned  
> to NAME[0].  The standard input of command is connected via a pipe to a  
> file descriptor in the executing shell, and that file descriptor is  
> assigned to NAME[1].

问题就在这里，如果大家都用 `COPROC` ，那么就没法分辨各个协程，没法精准向程序
输入或获取输出。所以 man page 中建议使用带有 `{}` 的格式。

一个例子

```bash
coproc STR_CAT {
    suffix="oh yeah"
    read line
    echo "$line $suffix"
}

echo hello >&${STR_CAT[1]}

cat <&${STR_CAT[0]}

# 输出
hello oh yeah
```

需要注意的是，如果 `coproc` 写在一行内 `{}` 内最后一条命令结束后需要 `;`，
否则 bash 识别不到 `}` 。

协程其实就是命名管道的简化，不需要通过文件，而是文件描述符即可与后台程序交流，
使用起来比命名管道更加方便。

```bash
str_cat() {
    suffix="oh yeah"
    read line
    echo "$line $suffix"
}

[ -p /tmp/soci ] || mkfifo /tmp/soci # str_cat out cat in
[ -p /tmp/sico ] || mkfifo /tmp/sico # str_cat in echo out

str_cat < /tmp/sico > /tmp/soci &

echo hello > /tmp/sico
cat < /tmp/soci

rm /tmp/soci /tmp/sico

# 输出
hello oh yeah
```

使用命名管道的方式明显看起来复杂。
